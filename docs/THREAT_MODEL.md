# Threat model

What could go wrong, how Guidewise stops it, and the test that proves it. "Probe" is `e2e/api-probe.mjs`, which runs against the live site on every release and every morning (`.github/workflows/live.yml`). "Unit" is a Vitest file in `tests/`.

| # | Threat | How it is stopped | Proved by |
| --- | --- | --- | --- |
| T1 | One visitor reads or changes another visitor's drafts, rules, facts or API keys | Every query is scoped to the caller's workspace id on the server; browsers never receive database credentials | Probe: "other workspace cannot read / act on / approve the draft", "other workspace's list / kit / export does not include it", "another workspace cannot see these keys" |
| T2 | A content creator approves their own draft, grants themselves an exception, changes rules or facts, or dismisses a critical finding; one reviewer alone approves high-risk content | Roles are enforced on the server for every action; only a reviewer (brand, compliance, brand manager) can dismiss a violation as an "Approved exception"; a high-risk draft needs two sign-offs, compliance first and then brand (Arjun or Meera), derived from the events log, and a later change to its findings voids the first sign-off | Probe: "creator cannot save rule / promote / save fact / delete fact / change kit / import / compile / approve", "brand cannot dismiss critical", "exceptions: a creator cannot grant an exception", "sign-off: brand cannot sign off before compliance", "sign-off: compliance alone does not approve a high-risk draft", "sign-off: the receipt names both approvers"; journey: "the brand reviewer cannot approve a high-risk draft", the two sign-off steps; unit: `workflow-rules.test.ts` |
| T3 | A draft is approved with problems still open, against rules that changed after it was checked, or on an exception that has expired | The approve action refuses while any violation is open; if the Brand Kit changed since the last check, the draft is checked again first and anything new blocks approval; an exception can carry an end date (stored in the dismiss reason, "Approved exception (until 2026-12-31)"), and once it has passed the finding reopens at the next re-check, at change impact and at approval itself; a database trigger (migration 009) also refuses to mark a draft approved while any violation is open, whatever writes to the database | Probe: "kit binding: approval re-checks against the new kit and refuses", "exceptions: an expired exception reopens on re-check", "exceptions: the reopened finding blocks approval", "exceptions: approval itself refuses a lapsed exception"; unit: `workflow-rules.test.ts`; journey: exceptions with an end date, then two sign-offs |
| T4 | An approved piece silently stops being true when a fact or rule changes | Change impact re-checks every draft that used it and sends broken approvals back for re-approval | Probe: the six "impact:" checks; unit: `impact.test.ts`, `seed-approved.test.ts` |
| T5 | The AI invents a finding, a quote or a fact | The verifier drops any finding whose quote is not in the draft, image or document, or whose rule or fact does not exist; numbers are compared by code | Unit: `fake-ai.test.ts` (a deliberately wrong AI), `campaign-ai.test.ts` ("drops a quote that is in no document") |
| T6 | Prompt injection in a draft ("ignore all previous instructions") | One rule per call with the draft fenced as data; output must match a Zod schema; the verifier still applies | Unit: `fake-ai.test.ts`, `hardcases.test.ts` (prompt-injection hard case), `fuzz.test.ts` |
| T7 | Personal data or confidential text reaches an AI provider | Emails, phones (mobile and landline), Aadhaar, PAN and card numbers are masked in code first; confidential drafts are never sent | Unit: `privacy-eval.test.ts` (0 leaks in 144 prompts), `campaign-ai.test.ts` (documents masked; confidential campaign never sent) |
| T8 | The server is made to fetch an internal address (SSRF) through "read a web page" | http(s) on standard ports only; every resolved address and every redirect is checked and private, loopback, link-local and metadata ranges are refused; 8 s and 2 MB limits | Unit: `webpage.test.ts`; probe: "web page: cloud metadata address refused", "web page: localhost refused" |
| T9 | Hostile input crashes a review or hangs the server (ReDoS, huge input) | Inputs are validated with Zod; rule regexes are checked for catastrophic backtracking before saving; email patterns are bounded | Probe: "rule with catastrophic regex", "too long draft", bad JSON on every route; unit: `fuzz.test.ts` (26 inputs, slowest 25 ms) |
| T10 | Hidden characters or hidden page text smuggle a claim past readers | Invisible characters are flagged and removed by the fix, then the checks run again; text a web page hides from readers (display:none, hidden, zero-size, transparent, same colour as its background) is separated, labelled and checked | Unit: `engine.test.ts`, `hardcases.test.ts`, `webpage.test.ts`; probe: "read a public web page" (the sample page hides one line) |
| T11 | A stolen or over-powerful API key | Keys are shown once and stored as SHA-256; scopes limit each key; revocation is immediate; every call is audited; 30 calls a minute per key | Probe: "a wrong key is refused", "a key without the scope is refused", "a revoked key stops working at once", "every call is in the audit trail" |
| T12 | Clickjacking, script injection or content sniffing in the browser | Content-Security-Policy allowing only this site (plus the OCR worker), no framing, nosniff, strict referrer and permissions policies, HSTS | Probe: "security headers: …" |
| T13 | Tampering with an approved text after approval | The receipt stores the SHA-256 fingerprint of the exact approved text and the Brand Kit version; approved drafts are locked | Journey: "approval record opens"; the record page shows the fingerprint |
| T14 | The AI service is down or rate-limited during a review | Fallback chain (Groq, Groq's smaller model, Gemini), time caps, a circuit breaker; without AI the code checks and the whole workflow still run, and the review says so | Unit: `providers.test.ts`; the review page labels "Code checks only" |
| T15 | A read-only share link is guessed, leaks, or exposes more than the record | The link carries 32 random bytes (base64url); only its SHA-256 hash is stored (as a `share_created` event), never logged and never returned by any API; look-ups are rate-limited per address; links expire after 30 days and a reviewer or the brand manager can revoke them (a creator cannot; another workspace cannot see or revoke them); unknown, expired and revoked links give the same 404; the public copy carries only the record (no workspace or draft id, no author, intent, images, documents or activity log), masks contact details and ID numbers in words that are not in the approved text, and is marked noindex and no-store | Probe: "share: …" (refused before approval, public copy without workspace id or hash, creator and other workspace cannot revoke, revoked and unknown tokens 404); unit: `share.test.ts`; sweep: "record: share a read-only link and open it outside the workspace" |
| T16 | Someone spoofs a role (x-role) or member headers on an organisation's (claimed) workspace, or opens it without signing in | `src/proxy.ts` runs before every workspace API route: a workspace with members needs a Supabase access token verified with `auth.getUser`, of one of its members; the member's stored role replaces x-role, and incoming member headers are discarded; no member cache, so a role change or removal applies on the next request; sign-in attempts are rate-limited per address. The `members` and `org_invites` tables are closed to the public key (no write grants; a user reads only their own member rows); every change goes through SECURITY DEFINER functions that check `auth.uid()` (claim only an unclaimed workspace, manager-only role changes and invites, last-manager guard), called with the user's own token; joining an organisation reads only `org_invites`, so a forged `invite_created` row in the open events table adds nobody | Probe: "accounts: …" (unauthenticated 401, forged member headers 401, non-member 403, direct REST insert into members refused, set_member_role and claim_workspace refused to a non-manager, forged invite event cannot add a member, x-role spoofing ignored, role change applies on the very next request, removed member loses access, last manager kept); unit: `accounts.test.ts` |

## Not covered

- Signing in is optional: a demo workspace (no members) is open to whoever holds its random id and can switch roles with "Acting as". An organisation's workspace is checked by the server, but the database still has the open demo policy; per-organisation row-level security is planned (`docs/KNOWN_ISSUES.md`, item 1).
- The API rate limit is counted per server instance, so it is approximate (known issue 11).
- The web page reader checks a host's addresses before each request but does not pin the address it checked (known issue 14).
